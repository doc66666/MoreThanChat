# 中心服务与通用插件扩展阶段（2026-10-11）

本阶段纠正两点：插件不再被视为输入框按钮；人与人聊天不再通过本地演示传输模拟。开发默认中心地址按用户要求使用 `http://localhost:8787`，没有配置公网地址。

2026-10-14 更新：本次群人数扩为 256（含创建人），建群／邀请／目录解析／回执和本机历史校验使用统一 `MAX_GROUP_MEMBERS`。客户端声明 `large-groups-v1`；不支持该能力的旧客户端加入超过 20 人的群后，收发和目录接口明确要求从仓库手动升级，未收消息不丢弃。中心与客户端需要一起升级，旧版服务器仍按旧上限拒绝请求。文件容量尚未扩展，仍为 5 MiB；当前内嵌附件按收件人复制，占全服 512 MiB 暂存预算，大群满尺寸附件会受预算拒绝。这是下一步要改的传输瓶颈，不声称 256 人满尺寸附件广播已支持。以下 20 人等旧阶段描述保留为历史记录。

产品边界同步纠正：中心的离线中继与旧声明式协议当前共享状态继续兼容，但不扩展为插件业务数据托管、自动备份或自动升级迁移服务。可执行插件应自行管理业务数据及升级行为；不能因用户升级插件就宣称业务数据已得到平台持久保障。真实人工体验由用户后续验收。

## 本机测试

启动开发中心服务：

```powershell
pnpm central:dev
```

另一个终端启动两个独立用户端：

```powershell
pnpm demo:clients
```

两个用户端分别保存到 `.artifacts/manual-central/client-a` 和 `client-b`，已有测试数据不会重置。旧窗口使用旧主进程时需完全关闭后重启，核心窗口不做热替换。

每端进入“设置 → 中心服务器 / 身份 / 联系人”，保留 localhost 地址，填写自己的名称，点击“Ping 并认证连接”。复制 B 的全局 ID，在 A 提交好友申请，再由 B 接受。好友会话和群会话都由本服目录建立；原有 AI 会话独立使用模型服务。

在联系人面板选择好友创建群。群成员可申请接龙、井字棋和通用同步通道，选择其显示位置。创建群的用户目前是唯一群管理员，审批后所有群成员获得相同的包版本。其他成员不能代替管理员审批。成员可单独停用本机界面；同步状态仍由中心服务维护。

新用户只预置 More AI，不再生成虚构的产品群、插件群或聊天记录。旧本地历史保留，但不自动转换成真实服务器群。新建单聊/群聊入口会转到中心服务。

## 全局身份与服务器范围

Main 首次生成 Ed25519 长期身份，私钥通过系统加密存储到 `host-private/identity-secret.bin`，不会交给 Renderer、插件或服务器。全局用户 ID 是 `usr_` 加规范 SPKI 公钥 DER 的 SHA-256；一个数据目录对应一个身份，重启和换服务器保持相同 ID。丢失身份文件会失去原 ID，当前尚未提供跨设备身份导入/恢复界面。

认证使用一次性、60 秒有效的挑战签名，绑定协议版本、服务器 ID、用户 ID 与随机 nonce。Ping 通只是第一步，持有有效签名且满足名单规则才能连接。会话令牌只在 Main 内存中保存。参考 [Node crypto](https://nodejs.org/api/crypto.html)。

独立服务器使用独立数据目录，产生 `srv_<UUID>`；群使用 `grp_<UUID>`，成员与管理员记录只归创建它的服务器。客户端历史按服务器 ID 分区，切换地址不会把 A 服会话发送到 B 服。没有跨服搜索、转发或好友联邦。

- `public` 模式：默认允许签名身份，执行黑名单。
- `private` 模式：只有被加入白名单的全局 ID 能认证。
- v0.4.0 起，模式可经管理员 CLI 在线切换并持久保存；启动环境仅提供初始模式，不会覆盖后续管理决定。
- 普通客户端设置中没有服务器管理员密钥。名单由服务运营者管理；群管理员只拥有本群成员和插件审批权限。

## 中继与离线送达

客户端通过经过认证的 HTTP 长轮询保持连接。消息到达时服务器立即唤醒挂起请求；离线端的消息保存在 `relay.sqlite/queue`，服务重启后仍在。

“送达”定义为客户端已校验数据、同步附件文件并提交本地 SQLite，然后发送 ACK。单纯收到 HTTP 响应不算送达。群聊按收件人分别确认，一人的确认不会删除其他人的副本。重复发送使用 sender/clientMessageId 去重，重复投递也在客户端去重。

ACK 或已读确认后删除该收件人的消息和附件转发副本。SQLite 开启 `secure_delete`，确认后 checkpoint/truncate WAL；不把消息正文写到服务器应用日志。服务器保留 ID、内容指纹和送达/已读计数等元数据，不保留已送达正文；全部收件人确认且发件人收到状态后，七天无进展的防重元数据可清理。未送达消息及未确认状态的防重记录不按时间删除，受总暂存容量限制。不承诺存储设备级的取证擦除。

身份、公钥、名单、好友关系、群成员、审批包和当前群插件状态是必要的服务数据，会继续保存。接龙条目、当前棋盘属于同步应用状态，不是聊天历史；插件更新后旧状态清空，只保留当前版本状态。服务器不提供已送达聊天记录恢复，用户需保留本地数据。

## 通用 UI 插件 SDK

### 内置 AI 作者上下文

PC Host 在每次模型对话请求起始处固定注入开发契约；不是依赖用户记得粘贴提示词，也不是只在创建插件时才提供。普通对话、重试、Host 重启后的请求及同一轮工具续调都携带它。聊天历史中的 system 消息只作为带标签的用户级上下文保留，不能让宿主契约漏传或获得宿主指令身份。

实现位于 `apps/pc-host/src/model-context.ts`，接口与能力清单位于 `apps/pc-host/src/author-contract.ts`；`inspect_drafts` 返回同一份契约。内容涵盖当前 PC 环境和可见信息、用户私有草稿空间、四个作者工具及参数、正确创建／诊断／修订流程、JSON 示例、实时共享状态的宿主代理和中心校验、缓存／重连／更新边界、布局插槽、用户与管理员的确认职责。它明确区分 AI 可创作的声明式插件与可信 UI 插件的内部 send/history/subscribe 接口，不将后者宣称为模型工具。

不对模型开放 shell、任意代码、文件／数据库、直接网络或管理员调用。安全仍由工具白名单、程序校验、执行预算、主进程授权和中心认证强制执行，提示词只是行为指导，不能保证模型永不出错或客户端绝不崩溃。本轮通过模拟 HTTP 响应检查真正序列化的请求与完整工具回包，未消耗真实 API 额度。

`ui.slots` 是新的贡献注册服务，生命周期仍由 `PluginRuntime` 管理，停用会撤销贡献。已有 `ui.composer-actions` 保留为一个小型接口，不再代表全部插件能力。

UI 插槽包括导航、侧栏、聊天标题、消息前后、详情面板、输入区前后及浮层。消息插槽上下文包含当前消息；可信 UI 插件通过 `render(context)` 返回自己的 React 组件，可实现任意组件形式。`chat.composer` 是可信插件替换输入区的入口，渲染异常有局部回退，不替换 Electron Main、存储和身份服务。界面区域有高度/滚动约束。

“工作区卡片”是输入框之外的生命周期示例。群包目前采用受限声明式 JSON（接龙、井字棋、同步通道），审批包含不可变版本和 SHA-256 摘要；客户端复核摘要，未经本群审批不能使用群通道。任意第三方 JS/TS 的隔离运行、编译打包和远程审核分发仍属后续阶段，不以“审批通过”代替沙箱。

窗口宽度不超过 1080 像素时，详情和群插件改为右侧抽屉，点击聊天标题右侧的信息按钮打开，抽屉内可关闭。不会再通过响应式样式彻底隐藏插件；验收包含 1024 像素窗口的打开、关闭及可见性检查。

```ts
const slots = context.getService('ui.slots')
context.contribute(slots, {
  id: 'my-panel',
  slot: 'chat.details',
  render: (ctx) => <MyPanel conversation={ctx.conversation} />,
})

const channel = context.getService('chat.network').forPlugin(approvedPackageId)
await channel.send(groupId, 'my-event', { position: 42 })
const stop = channel.subscribe(groupId, event => consume(event.id, event.payload))
context.effect(stop)
const recent = await channel.history(groupId)
```

通道绑定当前服务器、已审批包和群成员身份，不开放任意 URL、底层 socket 或认证令牌。事件先进入本机持久收件箱再确认，实时订阅按事件 ID 去重。接龙与井字棋的并发校验由服务器执行，revision 冲突会拒绝，不能由客户端伪造他人的落子。

首版后的事件缓存策略（2026-10-13）：`history` 是最近事件缓存，不是完整日志。每个服务器／群／插件最多返回 1000 条，按本机接收顺序排列；已确认事件全客户端合计最多保留 10000 条、16 MiB UTF-8 JSON 正文，因此单插件也可能少于 1000 条。额度不包括索引、WAL 和 SQLite 可复用空页，不代表数据库文件的物理大小上限。聊天历史、不可变插件包及当前共享状态不受此清理影响。声明式插件恢复界面以中心最新状态和 revision 为准，不能从可能截断的 history 重建完整棋局；通用通道作者也不能将订阅回调当作可靠的唯一状态存储。

只有服务器成功确认该设备 ACK 后，事件才进入可清理集合。ACK 请求失败、响应丢失或本地清理事务失败均保留待确认记录；下一轮／重启后先按批重交 ACK，再拉取新事件。旧 v5 数据库迁移为 v6 时，历史记录一律视为未确认，连接对应中心后补交；离线旧数据不会为满足配额被删除。正常新流量由每批最多 20 条及先清 ACK 的流程约束，遗留待确认记录暂不受上述缓存上限约束。服务器已确认并清理的事件依赖中心 ACK 后不再投递的协议保证，缓存不防御恶意中心重放。订阅回调不是跨进程崩溃的 exactly-once 执行：落盘后、回调前崩溃仍可能漏掉瞬时通知，应从状态／最近缓存恢复。

数据库升级不可逆向供旧版应用打开；已发布的 v0.1.0 不会覆盖此后的数据库。需要回退二进制时使用升级前的数据备份，不手工降低 user_version。

AI 创作的声明式群插件可使用上述 9 个受控位置，提交申请时由用户选择，位置随完整包一起审批；不是只能显示在侧栏，也不等于任意 DOM/CSS 或整个输入区替换。所有群插件视图只在当前选中的所属群内显示。消息前／后插槽会重复展示同一份共享状态，当前声明式表达式不提供该条消息内容。导航栏使用紧凑入口展开完整面板；浮层可以收起，面板内 Escape 会收起并返回入口焦点。收起只是隐藏视图，不停用、不撤销授权、不退出对局；停用仍使用本机插件授权按钮。位置变化作为包更新重新审批、重新确认。

## 输入与附件

默认输入区为左侧加号、中间文本、右侧按住说话；文本存在时显示发送按钮，Enter 发送，Shift+Enter 换行。加号菜单提供文件/图片选择和表情。语音松开发送，Esc/指针取消会取消，最长 60 秒。

文件和语音目前仅在本服好友/群会话中发送，单附件最多 5 MiB。附件以内容摘要存入本机仓库，不把大块 Base64 放进会话快照；收件端先同步文件再 ACK。图片与音频可预览，其他文件通过系统保存对话框下载。AI 模型会话暂不支持多模态附件。

只向本窗口的主 frame 授予音频媒体请求，不开放摄像头或子 frame 请求。真实麦克风仍受系统隐私设置控制。参考 [Electron session 权限接口](https://www.electronjs.org/docs/latest/api/session)。自动验收使用 Chromium 假设备，不采集用户实际声音。

## 自托管与开发限制

`pnpm central:package` 在 `.artifacts/central-release` 生成纯 Node 服务器目录，无 Electron 依赖。复制目录到 Linux，使用 Node 24.12.0 运行。数据目录应放在发布代码之外。

```sh
export MTC_SERVER_ADMIN_TOKEN='REPLACE_WITH_A_RANDOM_ASCII_SECRET_AT_LEAST_24_CHARS'
export MTC_SERVER_MODE=private
export MTC_SERVER_DATA_DIR=/var/lib/more-than-chat/private
export MTC_SERVER_HOST=127.0.0.1
export MTC_SERVER_PORT=8787
node server.mjs
```

将用户 ID 加入私服白名单（公共模式相同命令用于取消黑名单）：

```sh
node central-access.mjs allow usr_用户完整全局ID https://私服地址
node central-access.mjs deny usr_用户完整全局ID https://私服地址
```

本机开发脚本的管理员密钥保存在 `.artifacts/central-dev/admin-token`，CLI 可读取该文件，源码及客户端设置不包含密钥。远端配置必须使用 HTTPS 反向代理；直接远端 HTTP 被客户端拒绝。Linux 服务管理与安全配置见本文末尾的运维阶段，支持 `MTC_SERVER_ADMIN_TOKEN_FILE`，不必把令牌放入环境变量。

首版限制：每用户最多 500 个好友/申请、40 个群，每群最多 20 人、50 个包版本；单个自定义事件最多 32000 字符，服务器暂存预算 512 MiB。尚未实现公网运营所需的集群、端到端加密、完整限流/账号恢复、群多管理员与安全可执行插件沙箱。

## 验收

2026-10-12 的日常聊天补全阶段增加：

- Main 先将消息和发送队列同一个 SQLite 事务提交，再执行发送。退出、重启和断线不会丢掉待发记录；重连按原 clientMessageId 重试。队列按服务器 ID 分区。权限拒绝、内容冲突等永久错误转为失败，用户可明确重试；网络错误留在队列自动重试。
- 收件端持久保存后确认送达；只有原生窗口获得焦点、当前会话在最新位置且未被设置/搜索等弹层遮挡时自动标记阅读。离线阅读记录在重连所属服务器后补交。群聊显示送达人数和已读人数，服务器按收件人验证权限。
- 每会话的文字与附件引用草稿在当前用户的本地存储中保存。搜索范围明确为本机保存的聊天，可定位到消息；阅读旧消息时新消息不会拉走视图，提供回到最新消息按钮。消息按真实日期分段，界面先显示最近 50 条，历史由数据库分页取出。
- 会话可以置顶和免打扰，不提供归档或隐藏好友/群入口。未读通过会话徽标、窗口标题与任务栏闪烁提醒；系统通知见下方 2026-10-13 后续阶段，手机推送尚未实现。
- 好友申请可拒绝或取消，好友关系可移除。管理员可改群名、邀请、移出成员、转让管理员或解散；普通成员可退出。破坏关系的操作需要在用户界面明确确认。删除关系不删除本机历史；先前已经被服务器接受的消息仍可送达，并生成不可继续发送的历史会话。
- 中心协议仍为 v1，回执附加于已存在的 directory 事件，旧客户端可忽略；新客户端通过 Ping 的 feature 标识启用回执能力。持久目录 revision 防止并行请求返回旧目录后覆盖新状态。
- 已成功连接的服务器 ID 与地址关联保存。同一 ID 从另一个地址返回时，客户端在签名前要求明确确认迁移，避免将旧发送队列交给伪装地址；localhost 与同端口的回环地址视为同一地址。快速连续连接使用独立请求地址和取消信号，配置写入串行提交，仅保留最新连接。升级后的历史服务器需成功连接一次才能建立发送队列的地址绑定。
- 聊天原文、名称与文件名保留原样。程序凭据字段不会进入聊天存储，错误信息和有界诊断日志脱敏；设置中的模型 Key 继续由系统加密保存。用户主动输入的聊天内容属于聊天记录。

### 固定关系入口与历史分页（2026-10-12 后续阶段）

- 每个好友/群使用确定的同服会话 ID；旧归档标记升级后自动移除，不删除任何聊天记录。删除好友、退出/解散群后，关系入口消失，历史仍可通过本机搜索定位。重新建立相同好友关系复用原入口和历史，不生成重复入口。
- 群发送以服务器接受消息时的成员集合为准，排除发送者，每个收件人各有一份持久待送达记录。收件端 Host 先将正文和附件提交本机，再 ACK；服务器立即删除该收件人的正文副本，其他尚未确认的副本保留。拉取或在线本身不等于送达，送达不等于已读；删掉已送达副本不需要等待已读或其他成员上线。送达后只保留必要的防重和回执元数据，不保留正文。目前确认粒度是成员用户身份，不是同一用户的每台设备；多设备同步仍待后续实现。管理员黑名单/访问策略仍优先于送达。
- SQLite schema v4 保留既有数据，加入客户端消息查找、未读、恢复和 FTS5 trigram 索引。每次启动不读取全部历史；每会话初始最多 50 条，页面最多 100 条并受 512 KiB 正文预算约束，单条较大的合法消息允许独占一页，单条消息记录上限为 8 MiB。聊天历史总量不再受旧的 8 MiB 快照限制。
- 游标使用每会话持久、单调递增的位置，不依赖 OFFSET。更新回执或将临时发送 ID 换为服务器 ID 不改变位置；分页期间新消息不会改变旧页面边界。位置代表本机记录进入时间线的顺序，显示时间仍取消息时间；离线补发可能出现不同于服务器接受顺序的本地顺序。
- Renderer 获取的是有界近期投影；浏览旧历史使用独立页面，实时收件仍更新近期投影和未读，不把用户拉回最新页。支持更早/较新、搜索目标附近和返回最新消息。保存只增量 upsert 已加载记录，未加载部分不视为删除；服务器消息与回执只允许 Main 更新。
- 回执、防重和待发队列均按索引寻找记录，不局限于已加载页面。阅读最新会话会在 SQLite 事务中更新该会话全部未读记录，并将已读提交加入持久队列。重启恢复也覆盖首页外的中断 AI 回复，网络待发队列不变。
- 至少三字符的关键词用 FTS5 trigram 缩小候选，再进行原文子串校验；短中文关键词走参数化子串查询。每次最多返回 50 条、每条最多 360 字符摘要，完整正文通过定位页或 Main 的复制接口读取。诊断日志仍不作为完整同步事件源。

### 引用、转发与撤回（2026-10-12 后续阶段）

- 消息旁提供引用、转发和本人两分钟内的撤回操作。引用保存来源消息 ID，不把原文重复写入输入草稿；切换会话和重启后恢复引用。点击引用摘要通过 SQLite 游标定位原消息。撤回需要连接消息所属服务器，发送者离开群后仍可在时间窗口内撤回自己的已发送消息。
- 同服转发由 Main 从本机已接收记录读取原文和附件，不信任 Renderer 构造的内容；以新的 clientMessageId 排队和防重。文字、文件、图片、语音均沿原附件管线发送；复用相同内容摘要但文件名不同的附件不会篡改转发的原文件名。引用上下文不随跨会话转发复制，转发副本独立于原消息撤回。
- 协议 v1 增加可选 quote/forwarded/actionsSupported 字段与 directory.retraction 通知。中心新增 message_routes/route_recipients，保留原发送者、来源摘要/内容哈希、会话和初始收件人元数据；已送达正文仍删除。来源必须是发送者本人或初始收件人有权访问的消息，摘要与原文哈希校验不匹配时拒绝，不能用伪造的姓名/正文冒充来源。当前这些必要元数据长期保留，运营级元数据容量与保留策略仍待后续设计。
- 撤回权限和两分钟窗口由服务器时间校验；事务删除未送达原文、清除仍在服务器暂存的引用摘要，向发送者与原收件人分别投递无正文撤回通知。重复撤回使用同一通知和时间，不重新发送正文。已接受的回复/转发重试在来源后来撤回时仍正确防重。
- SQLite schema v5 新增持久 tombstone。Main 在确认通知前事务清除原文、附件引用、同服引用摘要及相关诊断副本，并从 FTS 中移除正文；不会删除共享的本机附件缓存或独立转发副本。首页之外的历史页同步更新，已撤回记录不会因迟到收件、旧快照或临时发送 ID 再次恢复。
- 客户端在认证时声明 message-actions-v1 能力，服务器不向旧会话交付撤回通知，也不允许旧会话将其 ACK 消耗；升级后再补同步。旧客户端已经保存的正文在升级前仍可能可见，因此不是远程安全擦除承诺。
- 已投递并清除正文的旧消息无法补计算可信摘要，默认不开放验证引用、转发和撤回，仍能搜索、定位与复制；仍在中继队列中的旧正文可以升级。不能为了兼容而悄悄将客户端提供的摘要当作已验证来源。

实时音视频、运营级限流/集群与大型历史压力/长期运行测试仍在后续范围；旧设备手动历史迁移见下方后续阶段。当前验收不等于运营级可靠性保证。

### 身份恢复和已登记设备同步（2026-10-13）

- 联系人 → 身份与设备：加密备份、导入、本机身份切换、本服设备列表和移除。备份要求 12–256 字符密码，固定 scrypt N=131072/r=8/p=1、随机 16 字节盐和 AES-256-GCM 随机 12 字节 IV，格式标识作为 AAD；算法参数不能由导入文件提升工作量。异步 KDF、8 KiB 文件上限，错密码/篡改拒绝。私钥仅在 Main 处理，Renderer 只传密码，文件通过系统对话框选择；不提供明文回退。密码不能重置。实现基于 [Node Crypto](https://nodejs.org/api/crypto.html#cryptoscryptpassword-salt-keylen-options-callback)。
- 导入验证后在独立目录暂存并原子发布，已有同 UID 空间复用，原目录不覆盖。本机选择指针原子更新；选中身份文件缺失时停止启动，不静默创建替代 UID。切换经过退出保存再重启，取消退出也取消切换。操作系统加密环境保持在应用根目录，聊天/附件/Host 设置用身份子目录，Renderer 用独立持久 session partition，避免切换 Chromium 加密环境导致已有凭据无法解锁。[Electron safeStorage](https://www.electronjs.org/docs/latest/api/safe-storage) 的 OS 密钥限制仍然适用；Linux 必须有真实密钥库。
- 备份仅包含身份凭据，不含消息、模型 Key、插件、草稿、设备 ID 和中心地址。新电脑导入后填写原中心地址，即可用原 UID 恢复该服关系。已经从中继清除的历史无法靠身份备份恢复。
- 协议 v1 协商 `device-delivery-v1`，认证挑战签入设备 ID；设备 ID 在本机生成并持久化，不从备份复制。中心新增 devices/queue_devices，原 queue 每用户仅存一份正文，另列目标设备快照；每台已登记设备分别落盘并 ACK，单台 ACK/已读只清除自身义务，最后一台完成或被移除才释放正文。无设备的旧用户保留 legacy 待收，第一台新版设备接管，后来登记的设备不补分已入队或已清除的历史。旧客户端不能消费已启用多设备身份的队列。
- 本人发出的新消息也送达其他已登记设备，按相同消息 ID 去重；已读与撤回为持久通知。送达人数依然按用户统计（任一设备收到即计入），不是设备完成率。离线设备没有自动过期，故意保留待收，可能占满原有 512 MiB 暂存预算；移除不用的设备可释放仅等待该设备的记录，最多登记 8 台。
- device_reads 仅保留每用户/消息的已读时间，用原收件人元数据校验权限，防止送达回执过期后跨设备已读失效或重试重复广播；同样属于需要运营容量策略的元数据。首次身份界面加载先持久化初始状态，再开放连接操作，避免新导入身份的联系人先出现、会话投影尚未建立的竞态。
- 本服设备移除撤销其现有会话并拒绝该设备 ID 再次登录，不删除它已落盘的内容；这是投递设备管理，不是根身份密钥吊销。持有身份私钥的人仍能用新设备 ID 登记。设备授权密钥分层/根密钥轮换、历史迁移、跨设备草稿/插件设置不在此阶段。
- 验收覆盖四个客户端、群与附件、发送者镜像、离线/中心重启、独立 ACK/已读、离线撤回、设备移除、旧版接管与防越设备 ACK、密码错误/篡改、身份空间不覆盖。桌面验收额外在两个独立 Electron 加密环境间导出/导入测试身份，启动第三个桌面端并检查同 UID 双向同步与身份设置 UI。

新增协议与服务测试覆盖签名认证、私服白名单、公共黑名单、跨服隔离、离线队列重启恢复、按收件人 ACK 清除、防重、审批权限和并发游戏校验。客户端测试覆盖身份稳定、附件校验和旧界面保存不能擦除已收件消息。

### 桌面通知与后台（2026-10-13 后续阶段）

### 手动聊天历史备份与迁移（2026-10-13 后续阶段）

#### 启动、停机与诊断

- 服务用独立 SQLite 锁文件持有操作系统锁，同一数据目录只能运行一个支持此锁的新版本实例；崩溃后锁自动释放。不要手动删除 `server.lock.sqlite`、SQLite WAL/SHM 文件，不要让旧版本、其它脚本或多个容器绕过锁共用数据目录。数据必须放在可靠的本机文件系统，不支持共享网络文件系统或多节点同时写入。
- 参数错误、数据占用、监听失败会退出非零并留下固定错误码日志，不回显令牌、请求正文、URL 查询、UID 或磁盘路径。`MTC_SERVER_ADMIN_TOKEN` 与 `MTC_SERVER_ADMIN_TOKEN_FILE` 二选一；令牌为 24–8192 个可见 ASCII 字符，令牌文件是至多 8 KiB 的普通文件，可有一个末尾换行。不要把令牌放进客户端、命令行参数或仓库。
- 环境中的白/黑名单只给**尚无管理记录的 UID**添加启动种子，不覆盖管理员后来设置的 allow/deny 或移除决定。v0.4.0 的管理 CLI 支持名单查询、添加、移除，以及在线切换 public/private 模式；私服空白名单拒绝所有身份。操作方法见[服务器快速入门](central-server-quickstart.md)。
- `GET /healthz` 仅报告进程存活；`GET /readyz` 检查运行状态及数据库中的服务器身份。它们不返回私有统计，也不等于磁盘可写、完整数据库校验或容量充足。关停先停止接入、结束长轮询，再等待已接收操作；默认 10 秒后中止未读完请求，所有处理结束后才关闭数据库。`MTC_SERVER_SHUTDOWN_TIMEOUT_MS` 可设 1–60000；systemd 停机超时应更长。[Node HTTP 关闭语义](https://nodejs.org/docs/latest-v24.x/api/http.html#serverclosecallback)
- `GET /v1/admin/status` 要求管理员 Bearer 令牌，仅返回用户/群/设备计数、待收行数、UTF-8 队列载荷字节、设备投递义务数、最老排队时长与运行聚合。`payloadBytes` 包括 JSON 和附件 Base64，并非原始附件大小。无消息正文、用户/设备标识、IP、令牌。`node central-status.mjs http://127.0.0.1:8787` 查询本机服务；仓库中可用 `pnpm central:status`。
- 基础保护为 1024 个连接、256 个活跃请求（包括长轮询），每身份/设备最多 2 个等待收件请求；拥堵返回带 `Retry-After` 的 429。内部故障返回脱敏 500，参数错误仍是 400。这不是完整的按身份速率限制或抗 DDoS 系统，公网仍需边缘防护和容量监控。
- 好友、群和插件审批的变化与目录通知入队为同一事务；配额或数据库写入失败会一起回滚，不再出现“操作成功但 API 报失败”的状态。512 MiB 是**新业务入队预算**；可信 ACK 衍生的、小型且按消息合并/按首次已读生成的控制通知不受该预算阻挡，避免满队列时 ACK 无法推进。实际总量可能暂时超预算，管理统计不会隐藏它；物理磁盘写满仍会明确失败，不能承诺零磁盘空间下继续服务。

#### Linux 单机部署模板

模板位于仓库 `deploy/central/`，发布包中为 `deploy/`。下面是供管理员执行的示例，不是已在用户远端完成的部署；将版本目录、Node 路径和域名换成实际值。使用非 root 服务账户，将代码与 `/var/lib/more-than-chat` 数据分开。

```sh
# 一次性创建账户与配置目录；若已存在，不要重复创建或覆盖原配置。
sudo useradd --system --home-dir /var/lib/more-than-chat --shell /usr/sbin/nologin more-than-chat
sudo install -d -m 0700 /etc/more-than-chat
# 将完整发布包放到 /opt/more-than-chat/releases/<版本>，current 指向该版本。
sudo install -m 0644 deploy/more-than-chat.service /etc/systemd/system/more-than-chat.service
sudo install -m 0600 deploy/server.env.example /etc/more-than-chat/server.env
# 独占创建随机令牌；文件已存在时会失败，绝不覆盖旧令牌。
sudo /usr/bin/node --input-type=module -e 'import{randomBytes}from"node:crypto";import{writeFileSync}from"node:fs";writeFileSync("/etc/more-than-chat/admin-token",randomBytes(32).toString("base64url")+"\n",{flag:"wx",mode:0o600})'
sudo systemd-analyze verify /etc/systemd/system/more-than-chat.service
sudo systemctl daemon-reload
sudo systemctl enable --now more-than-chat
curl --fail http://127.0.0.1:8787/readyz
sudo journalctl -u more-than-chat -n 50 --no-pager
```

先检查 `/usr/bin/node --version`，按实际安装路径调整 `ExecStart`。systemd 使用 `LoadCredential` 把 root 私有令牌提供给非 root 服务；`StateDirectory` 创建服务拥有的数据目录，`ProtectSystem` 等限制其它写入，`Restart=on-failure` 限定异常重启。服务启用不代表已就绪，应单独检查 `/readyz`。[systemd 服务定义](https://raw.githubusercontent.com/systemd/systemd/main/man/systemd.service.xml)、[执行隔离与凭据](https://raw.githubusercontent.com/systemd/systemd/main/man/systemd.exec.xml)

默认 Caddy 模板通过 HTTPS 转发至 loopback，并在公网入口拒绝 `/v1/admin/*`。管理 CLI 请 SSH 登录服务器后运行，使用原始令牌文件，例如 `sudo env MTC_SERVER_ADMIN_TOKEN_FILE=/etc/more-than-chat/admin-token /usr/bin/node /opt/more-than-chat/current/central-status.mjs`。私服先用同样的环境执行 `central-access.mjs allow usr_<完整ID>`。反代的响应头超时设为 35 秒，长于 25 秒收件等待；不启用包含 URL 标识的访问日志。合并配置后先执行 `caddy validate --config <配置文件>` 再启用；域名、证书、真实反代与防火墙需要管理员实际验收。[Caddy 代理配置](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy)

#### 升级与恢复规则

1. 把新包放进新的版本目录，不覆盖正在运行的代码或数据；先在测试数据上验收。
2. 停止旧服务并确认进程退出，再切换 `current`；不要双开共用数据。启动后检查同一服务器 ID、名单、关系与待收义务。

### 流量保护与短时负载（2026-10-13 后续阶段）

限流按已认证 UID，而非可更换的 session token、设备 ID 或未经验证的代理头计费。同身份多台设备共享对应额度；换账号仍可获得另一个身份的额度，所以这不是防女巫或抗 DDoS 机制。额度在进程内保存，重启重置，不跨节点共享；每类最多 8192 个 key，满时拒绝新 key，不驱逐活跃 key 来重置其额度，闲置五分钟可回收。未认证的 challenge/session 入口使用单独的全服预算，因此认证洪泛仍可能影响其他人的新登录；已连接用户的收件／确认和管理员诊断不与它共享额度。

| 请求类别 | 可突发请求数 | 每秒补充 | 计费范围 |
| --- | ---: | ---: | --- |
| challenge / session | 240 | 40 | 全服合计，认证前 |
| 成功验签后的新登录 | 16 | 0.5 | 每 UID |
| 发消息及普通修改操作 | 60 | 5 | 每 UID |
| 插件同步事件 | 120 | 20 | 每 UID |
| 目录等普通查询 | 120 | 10 | 每 UID |
| 收件 events | 120 | 20 | 每 UID |
| ACK、已读、登出、设备移除 | 240 | 40 | 每 UID |

- 超额返回 429 和秒数 `Retry-After`，不会执行对应业务变更；请求格式不合法仍消耗其类别额度。收件与确认分开，发送／插件／轮询刷请求不会消耗 ACK 额度。客户端已有持久队列将 429 当作暂时错误，约两秒后使用同一 clientMessageId 重试；新测试验证落盘、恢复发送和服务端防重。其他用户操作可以看到限流错误，不自动重放有歧义的群管理操作。
- 请求处理总上限仍是 256；普通请求在 224 时停止接入，余量用于 ACK、已读、登出、设备移除和管理员接口。保留名额只保护应用处理层，不是独立监听端口或 TCP 连接池；1024 个 TCP 连接也被占满时仍可能无法连接，需要边缘保护。每设备最多两个等待收件请求不变。
- 消息 JSON 上限 8 MiB，认证上限 8 KiB，ACK／已读／名单上限 16 KiB，其余请求上限 128 KiB；中文插件载荷按 UTF-8 字节考虑空间。消息请求体同时最多读取四个；已认证 UID 的普通和控制请求体各最多读取四个。管理员不受每 UID 限制，但仍受全局请求数和体积限制。声明长度提前校验，chunked 逐块计数；拒绝未读完的请求时返回错误并关闭连接，不继续无限排空请求体。大上传并发限制不是整个进程 RSS 上限，慢客户端的响应缓冲仍需后续专项验证。[Node 可读流迭代器](https://nodejs.org/docs/latest-v24.x/api/stream.html#readableiteratoroptions)
- challenge/session 容量边界修正为精确 1000／4096；会话容量检查在设备注册和用户写入之前，避免登录报满却部分生效。新登录时清理过期会话和过时在线活动记录，不改变磁盘身份／群／消息数据。

`pnpm verify:central-load` 构建独立包并运行 64 轮；也可 `node scripts/verify-central-ops.mjs --release .artifacts/central-release --load-rounds 8` 运行 CI 的短版。脚本仅使用新建临时数据和随机身份，不接触 `.artifacts/central-dev` 或真实用户数据。三名用户、四台登记设备发送群消息，每八轮每人携带一个真实 1 MiB 附件；每次发送再用相同 ID 重试。一台设备始终不收件，中途强杀并重新认证，最后按设备核对全部消息集合与附件哈希、补投和 ACK，检查队列行数／设备义务／载荷字节清零及 SQLite quick_check。遇到 429 按 Retry-After 重试；输出时延只是本机本次结果，不是容量保证。更大轮数可能超过离线预算，测试会明确失败而不是丢弃未送达数据。

本轮结果：构建和类型检查通过，测试合计 343 项通过、2 项 Windows 符号链接测试跳过。Windows 与 WSL Fedora Linux 的 Node 24.12.0 独立服务均完成 64 轮负载：192 条独立消息、576 次设备投递、24 条 1 MiB 附件消息，最大采样队列载荷 38,403,770 字节；最终三项队列统计均为零。最后一轮 Windows 用时约 22.8 秒、发送 p95 143 ms，Linux 约 13.1 秒、p95 94 ms；它们是不同运行环境和机器负载下的本机观测，不能外推吞吐量或公网 SLA。源码进程恢复、Windows 目录版完整聊天／插件／附件和后台通知回归也通过。没有调用真实 AI API、改动真实用户数据或部署公网服务；CI 已加入 8 轮负载，但未推送，远端执行状态未知。尚未完成小时级 soak、512 MiB 实体满队列压力、多用户大并发、慢响应背压和物理断电验收。

### 慢收件与持续运行（2026-10-13 后续阶段）

- 原来的请求处理计数不覆盖已交给 socket 但尚未发送完成的响应。现在序列化后超过 64 KiB 的响应单独计费：全服最多保留 64 MiB 序列化 UTF-8 载荷，每个已认证 UID 同时最多两个大响应；重登、换设备不改变身份范围。预算不足返回 429，单响应超过 32 MiB 返回 503，均在发送响应头前处理。小型 ACK、错误和健康／管理响应不占这个大响应预算。预算不等于整个进程 RSS 上限：JSON 查询／解析临时对象、UTF-16 字符串、SQLite 缓存、小响应、TCP／代理缓冲均另外占内存。
- 大响应每次最多写入 64 KiB UTF-8，写入返回背压时等待 drain 再继续；中文和 emoji 不会因 UTF-16 分块边界损坏。开始发送后的绝对期限为 30 秒，持续缓慢读取也不会无限占用。完成、网络断开、写入失败和超时都幂等释放计数／字节／监听器／定时器。超时会中止响应，客户端不能把半个 JSON 当作已收到。HTTP finish 仅说明数据交给传输层，不代表客户端已落盘；仍由原有独立 ACK 删除待收正文。[Node HTTP 写入与完成语义](https://nodejs.org/download/release/v24.12.0/docs/api/http.html#responsewritechunk-encoding-callback)
- 管理状态的 `runtime.outbound` 返回 active／bytes／peakBytes／rejected／timeouts；`runtime.memory` 返回 rssBytes／heapUsedBytes／externalBytes。只有管理员接口可读，不返回 UID、IP、消息或 socket 标识。CLI 对新聚合字段严格选择和验证，仍能读取没有这些可选字段的旧状态响应。bytes 表示仍持有的完整序列化载荷，不是 socket 未发送精确字节数；peakBytes 是当前进程自启动以来的高水位。
- 消息入队复用一条同步预编译语句，不再为每个收件人单独创建带大附件绑定的语句。Node 24.12 的原生绑定在重新绑定或语句销毁前保留；隔离内存实验中，300 次绑定 256 KiB 参数，逐次 prepare 的 RSS 从约 35 MB 到 115 MB，显式 GC 后回落；复用语句约 36 MB。显式 GC 仅用于定位实验，服务不启用。复用只消除这一类多份待回收绑定，仍可能保留最后一份参数，不能据此声称总体 RSS 稳定。新增注入 INSERT 失败、事务回滚、重试和重新绑定回归。[Node 24.12 SQLite 实现](https://raw.githubusercontent.com/nodejs/node/v24.12.0/src/node_sqlite.cc)
- `pnpm verify:central-soak` 使用临时服务和独立数据：先让同身份两个 TCP 客户端完全停止读取一个真实 5 MiB 附件，验证第三个大响应被拒绝、其他用户仍可收件／ACK，等待真实 30 秒期限，确认预算回零而消息仍有待收义务，然后正常收件并比对附件哈希。随后同一服务进程持续收发 180 秒，每八轮补收一次离线设备、验证所有设备集合并清空验证器的消息正文缓存；过程中不重启服务来掩盖累积问题。结束时检查队列和大响应预算清零、数据库 quick_check，并输出服务器进程内存采样与时延。原有强杀恢复测试仍在前置流程中，64 轮 load 模式仍在中途重启。
- 可用 `node scripts/verify-central-ops.mjs --release .artifacts/central-release --soak-seconds 3600` 延长到一小时。CI 配置 10 秒循环加真实 30 秒慢收件期限，属于短版，不称为小时级验证。脚本断言消息完整性、队列／响应计数归零及大响应预算，内存仅采样记录，不以某个 RSS 数值证明没有泄漏。此阶段未实现附件断点续传；极慢网络超过现有客户端或服务端期限后可能反复重试，仍需低速网络专项设计。元数据长期增长、断电／磁盘损坏、集群和公网压力仍不在已验收范围。

### 数据库语句复用与内存诊断（2026-10-13 后续阶段）

之前只复用入队 INSERT，权限、收件、回执和管理查询仍逐次 prepare。本阶段增加单数据库范围的语句复用层，最多缓存 128 条固定 SQL，按最近使用淘汰空闲项。参数始终独立绑定，不缓存查询结果，不改变磁盘格式、消息事务或 ACK 规则，也不修改 Node 数据库原型。Node 原生语句在重新绑定或销毁前可能保留参数，因此缓存数量不等于进程 RSS 上限；少量最后一次绑定仍可能留存。[Node 24.12 预编译语句接口](https://nodejs.org/download/release/v24.12.0/docs/api/sqlite.html#class-statementsync)

- get／all／run 执行期间独占语句；iterate 从首次读取到耗尽或 return 期间独占。相同 SQL 的嵌套读取使用独立临时语句，不重置已有游标；容量全被占用时不淘汰活跃项。暂态语句和淘汰项交由运行时回收，128 是缓存条数上限，不是所有原生对象的硬上限。
- 执行失败淘汰对应缓存项，原样报告错误，不自动重放 SQL。测试覆盖错误后重新绑定、事务回滚、表结构变化、游标提前退出／异常、同 SQL 重叠读取、缺失参数不沿用上一请求，以及写入成功但 RETURNING 数值转换失败时不重复执行。
- 管理员状态新增可选 `runtime.statements`：size／capacity／prepared／hits／active，分别表示缓存条数、容量、累计成功编译数、复用次数及正在执行的语句数。只返回计数，不返回 SQL、绑定值或身份；CLI 仍兼容旧状态响应。管理状态采样本身也会执行查询，因此这些计数是一次采样点，不是请求结束后的最终值。

`pnpm verify:central-memory` 使用随机临时服务与身份，先验证慢接收真实 30 秒期限，再在同一服务进程持续收发 600 秒。整个收发阶段不强制垃圾回收，不重启来清空内存；脚本同时断言固定负载的编译次数小于 128、没有遗留活跃游标、消息与附件正确且最终队列清空。RSS／JS heap／external 每轮采样，不设跨平台硬阈值，也不把回收后的低值当作运行峰值。

可选 `--memory-diagnostics` 仅在收发结束后启用一次诊断：测试子进程通过 `--expose-gc --import` 加载测试专用脚本，父子私有 IPC 请求返回回收前后内存数字和活跃资源种类计数。不开放 HTTP／Inspector 端口，不生成可能含消息或令牌的 heap dump。脚本不被复制进独立发布包，正常服务不导入、不启用强制 GC；不带此选项的原有验收命令仍照常运行。CI 使用十秒循环的短版加诊断，并非十分钟或小时级认证。需要延长时可运行 `node scripts/verify-central-ops.mjs --release .artifacts/central-release --soak-seconds 3600 --memory-diagnostics`。
